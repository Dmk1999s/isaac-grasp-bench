# WORKLOG

Phase 0(환경 구축)에서 실제로 막혔던 지점과 그 해결 과정.

이 문서의 요점은 "설치했다"가 아니다. **셋 중 둘은 에러를 내지 않고 실패했다** —
하나는 성공 종료 코드를 반환했고, 하나는 죽지도 않고 CPU를 태우며 매달렸다.
그래서 남길 가치가 있는 것은 해결책보다 **탐지 방법**이다.

## 1. 헤드리스에 stdin 이 없다 — EULA 프롬프트

**증상**

```
Do you accept the EULA? (Yes/No): Unable to bootstrap inner kit kernel: EOF when reading a line
EXIT=1
```

**원인**: `import isaacsim` 이 대화형으로 EULA 동의를 묻는다. 헤드리스에는 stdin 이 없으니
프롬프트가 즉시 EOF 를 받고 죽는다.

**해결**: `OMNI_KIT_ACCEPT_EULA=YES`. `scripts/setup_cache.sh` 가 만드는 환경변수 파일에
넣어 두어 인스턴스를 새로 띄울 때마다 따라오게 했다.

이건 셋 중 유일하게 **정직하게 실패한** 경우다. 종료 코드도 1이고 메시지도 원인을 가리킨다.

## 2. 성공했다고 말하면서 실패한 설치

**증상**: `isaaclab.sh --install` 이 **exit 0** 으로 끝났다. 그런데 `isaaclab` 이 없다.

```
$ pip list | grep isaaclab
isaaclab_assets   0.2.4      # 하위 패키지는 다 있는데
isaaclab_contrib  0.0.2
isaaclab_mimic    1.0.16
isaaclab_rl       0.4.7
isaaclab_tasks    0.11.12
                             # 정작 핵심 isaaclab 만 없다
```

**원인 추적**: 설치 로그 5만 자를 뒤져 나온 한 줄.

```
ERROR: Failed to build 'flatdict' when getting requirements to build wheel
  ...
  File "/tmp/pip-build-env-.../setuptools/build_meta.py", line 301
  ModuleNotFoundError: No module named 'pkg_resources'
```

연쇄는 이렇다:

1. `isaaclab` 이 `flatdict==4.0.1` 을 핀으로 고정한다
2. 그 버전은 휠이 없어 pip 가 sdist 를 빌드한다
3. pip 의 **빌드 격리**가 격리 환경에 *최신* setuptools 를 깐다
4. 최신 setuptools 에는 `pkg_resources` 가 없다. 그런데 `flatdict` 의 레거시 `setup.py` 는 그걸 import 한다
5. 빌드 실패 → `isaaclab` 설치 실패 → **그런데 래퍼 스크립트는 0 을 반환한다**

정작 venv 자체의 setuptools 는 79.0.1 이라 `pkg_resources` 가 멀쩡히 있었다.
문제는 격리 환경이 그걸 안 쓴다는 것이었다.

**해결**: 빌드 격리를 끄고 venv 의 setuptools 를 쓰게 한다.

```bash
pip install --no-build-isolation "flatdict==4.0.1"   # 먼저 이 경로를 막고
./isaaclab.sh --install                              # 그 다음 본 설치
```

**재발 방지**: 종료 코드를 믿을 수 없으므로 `setup.sh` 가 설치 후 직접 확인한다.

```bash
if ! pip show isaaclab >/dev/null 2>&1; then
  log "ERROR: 핵심 isaaclab 패키지가 설치되지 않았다."
  return 1
fi
```

**교훈**: 래퍼 스크립트의 종료 코드는 그 안에서 돈 pip 의 종료 코드가 아니다.
설치 검증은 "설치 명령이 성공했는가"가 아니라 **"물건이 거기 있는가"** 로 해야 한다.

## 3. 죽지 않고 41분간 매달린 학습

가장 잡기 어려웠던 것. 타임아웃도, 에러도, 로그도 없었다.

**증상**: 헤드리스 학습을 띄웠는데 41분 동안 로그가 한 줄도 안 늘었다.
그런데 프로세스는 살아 있고 **CPU 를 111% 쓰고 있었다.** GPU 사용률은 0%.

```
PID    STAT  ELAPSED   TIME      %CPU
34441  RNl   41:55     00:46:34  111
```

`STAT=R` — I/O 대기가 아니다. 뭔가를 열심히 하고 있는데 진행이 없다.
이런 건 로그만 봐서는 어디서 도는지 알 수 없다.

**진단**: 살아있는 프로세스의 파이썬 스택을 그대로 떴다.

```bash
sudo env "PATH=$PATH" py-spy dump --pid 34441
```

```
Thread 34441 (active+gil): "MainThread"
    do (usd/commands/usd_commands.py:4587)
    spawn_preview_surface (isaaclab/sim/spawners/materials/visual_materials.py:69)
    _add_markers_prototypes (isaaclab/markers/visualization_markers.py:351)
    _set_debug_vis_impl (isaaclab/envs/mdp/commands/pose_command.py:135)
    ...
    make (gymnasium/envs/registration.py:734)
```

디버그 시각화 마커의 **머티리얼 생성** 단계였다. 정상이면 수 초 걸리는 구간이다.

그러고 나서 로그를 다시 보니, 41분 전에 딱 한 줄 남아 있던 에러가 눈에 들어왔다.

```
[Error] [rtx.neuraylib.plugin] Failed to open .../libneuray.so:
        libGLU.so.1: cannot open shared object file: No such file or directory
```

**원인**: Deep Learning AMI 에 `libGLU.so.1` 이 없다. 렌더링 플러그인이 로드되지 못하는데,
Isaac Sim 은 거기서 죽지 않고 머티리얼 생성 단계에서 무한정 매달린다.
에러 한 줄만 남기고 진행이 멈추므로, 로그만 보면 "조용히 멈춘 것"처럼 보인다.

**확인**:

```bash
$ ldd .../libneuray.so | grep "not found"
        libGLU.so.1 => not found
```

**해결**: `libglu1-mesa` 설치. 같은 계열의 누락을 한 번에 막기 위해 Isaac Sim 헤드리스
표준 의존성을 함께 깔았다 (`libxrandr2`, `libxinerama1`, `libxcursor1`, `libxi6` 등).

**결과**: 41분 매달리던 같은 작업이 **1분 안에** 끝났다.

```
Learning iteration 4/5
Computation: 1453 steps/s (collection: 0.410s, learning 0.119s)
EXIT=0
```

5 iteration 전체로는 워밍업 1회(265 steps/s)를 빼고 **1453~1545 steps/s**,
iteration 당 **0.50~0.53 s** 였다.

**교훈**: 멈춘 프로세스를 볼 때 먼저 물어야 할 것은 "죽었나"가 아니라
**"살아서 뭘 하고 있나"** 다. `STAT`/`%CPU` 로 살아있음을 확인하고,
`py-spy dump` 로 스택을 뜨면 로그가 없어도 위치가 나온다.
그리고 무해해 보이는 `[Error]` 한 줄이 41분짜리 정지의 원인일 수 있다.

## 부수적으로 정리한 것

- **의존성 핀 정렬**: 위 설치들이 `packaging` 을 26.3 으로 밀어 올렸는데
  `isaacsim-core` 는 `packaging==23.0` 을 명시 고정한다. `click`/`psutil`/

  `pip check` 기준 isaacsim/isaaclab 충돌 0건으로 맞췄다.

- **남은 충돌 (의도적)**: `stable-baselines3` 가 torch≥2.8 을 요구하지만 2.7.0 을 유지한다.
  Isaac Sim 5.1 공식 조합이 2.7.0 이고, 이 프로젝트는 `rsl_rl` 을 쓴다.
  sb3 를 쓸 일이 생기면 그때 재검토한다.

- **학습 산출물 위치**: `rsl_rl` 은 기본적으로 `$ISAACLAB_DIR/logs` 에 체크포인트를 쌓는데
  거기는 루트 볼륨이다. `~/IsaacLab/logs` → `/data/isaac-grasp-bench/runs` 심볼릭 링크로
  영속 볼륨에 떨어지게 했다.

- **캐시**: Omniverse/pip 캐시를 인스턴스 스토어(`/opt/dlami/nvme`)로 돌려 루트 볼륨을 아꼈다.
  **stop 하면 소실된다.** `scripts/setup_cache.sh` 가 재구축 스크립트이며,
  인스턴스를 start 할 때마다 실행해야 한다. 소실되는 것은 캐시뿐이다.

# Phase 1 — 베이스라인 구축에서 막힌 것

## 4. RTX 렌더러가 이 인스턴스에서 초기화되지 않는다

뎁스 카메라를 붙이자 `env` 생성 단계에서 세그폴트가 났다.

```
Thread: __enable_hydra_engine (omni/kit/widget/viewport/impl/texture.py:377)
네이티브: librtx.scenedb.plugin.so!carbOnPluginStartup
```

**격리**: Isaac Lab **공식 예제**(`scripts/tutorials/04_sensors/run_usd_camera.py`)도
동일하게 세그폴트했다. 내 설정 문제가 아니다.

**부분 해결**: Vulkan 로더가 아예 없었다.

```
$ ls /usr/share/vulkan/icd.d/     -> 디렉터리 자체가 없음
$ ldconfig -p | grep vulkan       -> 없음
```

`libvulkan1` 설치 후 `vulkaninfo --summary` 가 A10G 를 인식한다(1.4.329).
NVIDIA ICD 는 `/etc/vulkan/icd.d/nvidia_icd.json` 에 이미 있었고 로더만 없었다.

**그러나 여전히 세그폴트한다.** RTX 씬 DB 플러그인 시작 실패는 미해결이다.
`libGLU`, `libXrandr` 등 시스템 라이브러리 누락은 전부 해소한 뒤의 상태다.

**우회**: `RayCasterCamera` 는 RTX 를 쓰지 않지만
**정적 단일 메시만 지원**한다(소스 주석 명시). 움직이는 큐브에는 쓸 수 없다.

**현재 선택**: 물체 자세 + 알려진 형상에서 '한 시점에서 보이는 면'만 샘플링한
합성 점군을 쓴다 (`src/synthetic_cloud.py`).
이건 환경 제약 때문만이 아니라 **실험 설계상 오히려 타당하다** —
비교 대상 RL 정책이 상태 관측을 받으므로, 휴리스틱에만 카메라를 주면
차이에 '관측 양식'이 섞인다(원칙 1 위반). 자세한 근거는 그 파일 상단 참고.

## 5. 하네스가 아무것도 재고 있지 않았다 — 대조군이 잡아낸 것

첫 베이스라인 실행은 **성공률 100%, 반복 편차 0.0%p** 를 냈다.
물체 초기 위치가 무작위인데 사이클타임이 소수점까지 같았다. 믿을 수 없는 값이다.

**대조군**: 파지 자세를 일부러 x 방향 20cm 어긋나게 줬다.
→ **역시 100%.** 하네스가 파지를 재고 있지 않다는 뜻이다.

**원인**: 안착 15스텝 + 본 루프 250스텝 = 265 > 에피소드 예산 250.
루프 도중 환경이 자동 리셋되고, 리셋 직후 큐브 스폰 높이(z=0.055)가
성공 기준(0.04)보다 높아 그 순간이 성공으로 집계됐다.
사이클타임 4.68s(=234스텝)가 정확히 그 시점이었다.

**해결**: 판정을 `env.step` **이전** 상태로 하고, 종료된 env 는 `active` 마스크로 제외.
남은 예산만큼만 루프를 돈다.

**교훈**: 성공률 100% 와 편차 0 은 축하할 값이 아니라 **의심할 값**이다.
의도적으로 틀린 입력을 넣어보는 대조군 한 번이 이걸 잡았다.

## 6. 플랜지 자세 vs TCP — 오프셋 이중 적용

수정 후 성공률이 0% 가 됐다. EE 는 목표에 0.004m 까지 도달하는데 물체는 안 들린다.

**원인**: 휴리스틱의 `poses["grasp"]` 는 **플랜지** 자세다(z=156mm).
그런데 IK-Abs 액션은 `body_offset=[0,0,0.107]` 로 **이미 TCP 기준**이다.
플랜지 자세를 명령하면 손끝이 103mm 위에 뜬다.

**해결**: `poses["fingertip_grasp_position"]`(z=53mm)을 목표로 준다.

## 7. 실기용 상수가 조용히 발목을 잡는다

`compute_grasp` 이 모든 env 에서 예외를 냈는데 내 `except` 가 삼켜서
**폴백(물체 실제 위치)이 대신 돌고 있었다.** 그 결과 93.8% 라는
"휴리스틱 성능이 아닌" 숫자가 나왔다. 예외 사유를 출력하도록 고쳐서 잡았다.

원인은 인자 라우팅 실수였다 — `grasp_depth_mm` 은 `create_grasp_poses` 의 인자인데
`compute_grasp` 에 넘기면 `**kwargs` 를 타고 `calculate_3d_pca` 로 흘러가 TypeError 가 난다.

그 뒤 드러난 실기 상수 두 개:

| 상수 | 원본 값 | 큐브에서 생기는 문제 |
|---|---|---|
| `GRASP_ALONG_AXIS_DEEPER_MM` | 20.0 | 파지점을 주축으로 20mm 밀어 48mm 큐브 **밖으로** 내보낸다 |
| `FLOOR_CLEARANCE_MM` | 30.0 | 손끝 z 를 30mm 아래로 못 내려가게 클램프한다 (큐브 중심이 24mm) |

둘 다 실기 작업대 기준으로 튜닝된 값이고, 파라미터로 노출돼 있어
알고리즘을 건드리지 않고 조정할 수 있다.

## 8. 수치 노이즈보다 작은 임계값 — 점군이 통째로 어긋난 이유

앞의 버그들을 다 고쳤는데도 성공률이 12.5% 에 머물렀다.
스텝별로 계측해보니 그리퍼가 **0.0002 까지 완전히 닫혔다** —
큐브가 손가락 사이에 있었다면 0.021 부근에서 걸렸어야 한다. 허공을 집고 있었다.

좌우를 보니 물체 `(0.479, 0.019)` 대 목표 `(0.492, 0.003)`, 약 20mm 어긋나 있었다.
그런데 **점군 중심부터 이미 어긋나 있었다**:

```
물체 중심 = (478.6, 19.0, 21.0) mm
점군 중심 = (486.1, 11.1, 28.9) mm     <- 파지 계산 이전에 이미 틀렸다
```

점군 생성기를 같은 입력으로 오프라인에서 돌리면 정상이었다.
같은 프로세스 안에서 하드코딩 입력과 실제 인자를 나란히 돌려보니

```
[하드코딩] z고유값=1종    중심=(478.7, 18.3, 45.0)    <- 윗면만. 정상
[실제인자] z고유값=410종  중심=(486.1, 11.1, 28.9)    <- 옆면까지 샘플링됨
```

**원인**: 시뮬레이터가 주는 물체 쿼터니언이 정확한 항등원이 아니었다.

```
w = 0.99999994,  x = -4.5055594e-06,  y = -4.6998775e-06,  z = 7.8002444e-07
```

기울기로 환산하면 0.03도 — 물리적으로는 완전히 무시할 값이다.
그런데 내 가시성 판정 임계값이 `-1e-6` 이었다. **잔차(~5e-6)보다 작다.**

시선과 정확히 수직인 옆면 4개는 내적이 이론상 0 이지만, 이 잔차 때문에
부호가 노이즈로 정해졌고 그 결과 '보이는 면'으로 분류됐다.
옆면은 물체 높이 전체(-3~45mm)에 걸쳐 있어 점군 중심이 통째로 끌려갔다.

**해결**: 임계값을 각도 기준으로 바꿨다. `min_facing = 0.1`(입사각 약 84도).
스치는 각도의 면은 실제 뎁스 카메라에서도 픽셀이 거의 안 잡히므로 물리적으로도 맞다.

**결과**: 성공률 12.5% → 87.5%. 점군 중심이 물체 중심과 일치한다.

회귀 테스트에 그 쿼터니언 값을 그대로 박아뒀다
(`test_near_identity_quaternion_does_not_leak_side_faces`).

**교훈**: 부동소수점 비교의 임계값은 '0 에 가까운 아무 값'이 아니라
**입력이 실제로 갖는 노이즈보다 커야 한다.** 시뮬레이터의 '항등원'은 항등원이 아니다.
그리고 이 버그는 예외도 경고도 내지 않았다 — 성공률만 조용히 낮췄다.

## 부수 발견 — USD 바운딩박스가 실제 충돌 형상과 다르다

큐브 크기를 USD 바운딩박스로 재면 48mm 인데, 안착 높이(중심 z=21.0mm)에서

# 최종 베이스라인

버그 5건을 고친 뒤의 측정 (10회 반복 x 32 env = 320 에피소드):

| 지표 | 값 |
|---|---|
| 성공률 | 95.6% (표준편차 2.6%p) |
| 사이클타임 | 1.74s (표준편차 0.01s) |
| 대조군(20cm 어긋난 파지) | 0.0% |

**반복 편차 2.6%p 가 이후 비교의 판단 기준이다.**

원본 기본값(`grasp_depth_mm=5`)에서는 0.0% 다 — `grasp_clearance_mm=10` 보다
작아 손끝이 접촉점 위에 멈춘다. `depth > clearance` 를 만족하는 최소값 15mm 를 썼다.
성공률을 보고 고른 값이 아니다.

# Phase 2~4 — 격자가 아니었으면 못 찾았을 버그

## 9. 90도 어긋난 그리퍼 프레임 — 정사각 물체에서는 무증상

기본 Lift-Cube 조건에서 PCA 휴리스틱과 PPO 정책이 **둘 다 성공률 100%** 로 나왔다.
천장 효과라고 결론내고 넘어갈 뻔했다. 그래서 물체 형상을 바꿔가며 훑었더니:

| 물체 (mm) | PCA 성공률 |
|---|---|
| 42 x 42 x 42 (정사각) | 100.0% |
| 63 x 42 x 42 (길쭉) | 20.0% |
| 84 x 42 x 42 (더 길쭉) | **0.0%** |

길쭉해질수록 무너진다. 그런데 **휴리스틱은 한 번도 "못 잡겠다"고 하지 않았다**
(`heuristic_failed = 0/160`). 84mm 는 Franka 개방 한계 80mm 를 넘는데도
휴리스틱은 "42mm 축으로 닫으면 된다"고 판단하고 있었다. 즉 **의도한 축과
실제로 닫히는 축이 다르다.**

**원인**: 두 프레임 규약이 다르다.

```
휴리스틱  : 닫힘축 = tool_x  (회전행렬 1열)
             grasp_pca_core._measure_grasp_width() 가 tool_x 로 폭을 잰다
Franka Hand: 손가락은 panda_hand 프레임의 y 축으로 벌어진다
```

90도 어긋난다. **정사각 큐브에서는 대칭이라 어느 축으로 닫든 결과가 같아
아무 증상이 없다.** 길쭉한 물체라야 드러난다.

**검증**: 추측으로 고치지 않고, 명령 자세를 tool_z 기준으로 돌려가며 측정했다.

```
84x42mm 물체, 보정 없음  ->   0.0%   (84mm 축으로 닫으려 함 — 한계 초과)
84x42mm 물체, 90도 보정  -> 100.0%   (42mm 축으로 닫음)
```

**해결**: 어댑터에 규약 변환을 넣었다 (`isaac_adapter.heuristic_rot_to_franka_hand`).
접근축 tool_z 는 보존하고 그 축 기준으로만 돌린다.
회귀 테스트도 추가했다 — 그리퍼는 대칭으로 닫히므로 닫힘축은 방향이 아니라 '선'이고,
따라서 부호는 비교하지 않는다(+90 과 -90 은 물리적으로 같다).

수정 후 정사각 큐브에서 다시 재보니 100.0% 로 동일했다 — 무증상이라는 것도 실측했다.

**교훈**: 성공률 100% 가 두 방식에서 동시에 나왔을 때 "천장 효과"로만 읽으면
안 된다. 그 조건이 **버그를 가리고 있을 수도** 있다.
대칭적인 테스트 대상은 비대칭적인 오류를 숨긴다.
실패 지도를 그리는 목적이 성능 비교만이 아니라 여기에 있다.
